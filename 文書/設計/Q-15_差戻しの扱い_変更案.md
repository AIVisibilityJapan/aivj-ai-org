# Q-15 監査の「差戻し」の扱い — 変更案（実装前の確認用）

作成: 2026-11-05 ／ 状態: **社長承認・実装済み（2026-11-05、D-043）。社長の回答: §5-1 はすべて差戻し（SHA 不一致を含む）、§5-2 は通常（mid）、§5-3 は通知なし。追加の指示: 差戻しがあっても勝手に変更せず、変更するかを確認し、変更したら見直せるようログを残す（ログは 1 ファイルに加筆）** ／ 関連: 判断ログ D-041・D-042、STEP4_試験設計.md §11

## 1. 何が問題か（実際に起きたこと）
STEP 4 の連携試験（糸島市・原本のひな形）で、独立監査が「不合格（協会名・住所の不備）」と判定した。これは**正しい判定（正常な結果）**だが、現在の基盤は次のように動いた。

| 順 | 起きたこと | 問題 |
|---|---|---|
| 1 | 監査の工程が『失敗』として記録される | 故障ではなく判定なのに、失敗と同じ扱い |
| 2 | 同じ入力で 2 回再試行される（max_retries=2） | 結果は毎回同じ。時間の無駄で、ログも汚れる |
| 3 | 再試行上限で『失敗』が確定し、役割の「連続失敗」が 1 増える | 3 件続くと AI-06-06 が**自動停止**する |
| 4 | 自動停止すると、AI-06-06 が担当する**ほかの案件の監査も止まる** | 1 件の不合格が、監査全体を止める。再開は社長の操作が必要 |
| 5 | 人間キューに「失敗（再試行上限）」「自動停止」が載る | 『差戻し』（直して出し直す）と『障害』（原因調査）の区別がつかない |

実データの試験では、人間キューに「失敗（再試行上限）」と「自動停止: AI-06-06」が載った。

## 2. 現在の動作（コードの場所）
- `src/orchestrator/coo.py` `_run_ready`: 処理（handler）が例外を出すと、種類を問わず `engine.fail()` を呼ぶ。
- `src/orchestrator/task_engine.py` `fail()`: 試行回数が `max_retries` 以内なら `queued` に戻して再試行。超えたら `failed`。どちらも `_auto_stop_if_needed()` で連続失敗を 1 増やし、`consecutive_failures_to_stop_role`（現在 3）に達すると役割を停止ファイルに書く。成功で連続失敗はリセット。
- `coo.py` `_exceptions`: `failed` のタスクを人間キューへ（「失敗（再試行上限）」）。`_update_projects`: failed／blocked があれば案件は `attention`。

## 3. 変更案
### 3.1 新しい結果「差戻し」（`rejected`）
工程の処理が、**明示的に**「再試行しても変わらない理由で、先へ進めない」と返したときの結果。処理側は専用の例外 `Rejected(理由)` を出す。**ほかの例外（想定外のエラー・通信エラー等）は、今までどおり『失敗』で再試行・自動停止の対象**。

| 項目 | 失敗（今まで・変更なし） | 差戻し（新設） |
|---|---|---|
| 意味 | 想定外のエラー・応答なし・費用ガード | 判定・検査の結果、先へ進めない（直して出し直す） |
| 再試行 | する（上限まで） | **しない**（1 回で確定） |
| 連続失敗への加算 | する | **しない** |
| 役割の自動停止 | 連続 3 回で停止 | **対象外** |
| 人間キューの題 | 「失敗（再試行上限）」 | 「差戻し: 〇〇」＋理由（監査の指摘など）と、直し方の案内 |
| 案件の状態 | attention | attention |
| 後続の工程 | ブロック | ブロック（走らない） |
| 管理画面 | 「失敗」 | 「差戻し」（別の欄・色） |

### 3.2 再開のしかた
差戻しになったタスクは**そのまま再実行しない**（同じ入力は同じ結果になるため）。人が原因（ひな形・根拠データ・設定など）を直したうえで、**新しい案件番号で登録し直す**。履歴は残る（差戻しの理由・日時・実行者が実行ログに残る）。

### 3.3 変更するファイルと範囲（小さな追加）
| ファイル | 変更 |
|---|---|
| `src/orchestrator/task_engine.py` | 状態 `REJECTED` を追加し、`TERMINAL` に含める。`reject(task_id, worker, reason)` を追加（再試行なし・連続失敗に加算なし・停止なし・実行ログに記録）。依存の判定（`_dependency_state`）で、差戻しを『後続はブロック』扱いにする |
| `src/orchestrator/coo.py` | `Rejected` 例外を捕まえて `engine.reject()` を呼ぶ（他の例外は従来どおり `fail()`）。`_exceptions` に、差戻しの人間キュー登録（重複しない）を追加。`_update_projects` で差戻しも attention |
| `src/admin-ui/build_dashboard.py` | 状態の表示名「差戻し」と、注意欄への表示（既存の「失敗」「ブロック」と同様） |
| `src/aiv/free_report_flow.py` | `AuditRejected`・`ReaderStop`・`FillStop` を `Rejected` として返す（§5 の確認事項 1） |
| 試験 | §4 |
| 文書 | 判断ログ（D-043）、IMPLEMENTATION_PLAN、MASTER_PLAN（Q-15 を完了へ）、STEP2 の定義（運用手順書に『差戻し』を追記） |

### 3.4 変わらないこと（安全面）
- 費用ガード（上限 0・超過で停止）、承認の関門（社長の承認前に走らない）、緊急停止・手動停止、再開の実行者必須、冪等キー、排他ロックは**変更しない**。
- 未設定の上限は起動しない（fail closed）。
- 差戻しは人間キューに必ず載る（黙って止まらない）。

## 5. 社長に確認してほしいこと
1. **どの理由を『差戻し』にするか**（STEP 4 の工程）
   - (a) 監査の不合格（協会名の不備など）… 差戻し（推奨）
   - (b) 差し込みの停止（対応表にない項目・値が空・パラメータ未指定）… 差戻し（推奨）
   - (c) 自治体が見つからない・重複、根拠データの内部の食い違い … 差戻し（推奨）
   - (d) **値ファイルの SHA が固定と違う**（データが変わった可能性）… 推奨は差戻し（再試行しても変わらないため）。ただし『改ざん・破損の警報』として扱うなら、従来の『失敗』（再試行・連続で役割停止）のままにする選択もある。**判断をお願いしたい。**
2. **差戻しの人間キューの優先度**: 通常（mid）か、監査の不合格のみ高（high）か。推奨: 通常（mid）。
3. **差戻しの回数の見張り**: 同じ役割が短期間に差戻しを多発した場合の通知を付けるか。推奨: 今は付けない（管理画面で件数が見えれば十分。必要になったら追加）。

## 8. 運用（社長の追加指示を反映）
1. 差戻しが起きる → 人間キューに『差戻し: 役割 工程』が載る。理由と**変更すべき箇所**が書かれる。**原因の箇所は自動では変更しない。**
2. 社長が、変更するかしないかを決める（Claude が確認する）。
3. 決まったら、差戻しログに『確認結果』を 1 行加える。変更した場合は『変更の実施』（変更した内容と**見直し方＝元に戻す方法**）を 1 行加える。
4. 直したら、新しい案件番号で登録し直す。
- 差戻しログは **1 ファイル**（`データ/実行状態/差戻しログ.md`）。新しい順に上へ加筆し、既存の行は書き換えない。一覧の表で、発生・確認・変更が一目で分かる。
- 行の追加: 発生は AI COO が自動で加筆。確認結果・変更の実施は `py scripts\rejection_log_add.py --kind …`（Claude が変更したときも同じ）。『変更の実施』は見直し方の記入が必須。
